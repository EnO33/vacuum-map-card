### How the call resolves

Code path at 2026.11.2: `batched_entity_service_call` ([helpers/service.py#L955-L989](https://github.com/home-assistant/core/blob/2026.11.2/homeassistant/helpers/service.py#L955-L989)) resolves the targeted entities, then `_async_clean_area` ([services.py#L27-L86](https://github.com/home-assistant/core/blob/2026.11.2/homeassistant/components/vacuum/services.py#L27-L86)) runs once with all of them.

1. Candidates: entities the user may control ([helpers/service.py#L649-L693](https://github.com/home-assistant/core/blob/2026.11.2/homeassistant/helpers/service.py#L649-L693)); **unavailable entities are dropped** ([L743](https://github.com/home-assistant/core/blob/2026.11.2/homeassistant/helpers/service.py#L743)); explicitly referenced entities that are missing or unavailable are only logged as a warning ([L754-L760](https://github.com/home-assistant/core/blob/2026.11.2/homeassistant/helpers/service.py#L754-L760), [helpers/target.py#L160-L179](https://github.com/home-assistant/core/blob/2026.11.2/homeassistant/helpers/target.py#L160-L179)).
2. Feature filter (table above). If no entity is left and no response was requested, the call **returns without error** ([helpers/service.py#L791-L796](https://github.com/home-assistant/core/blob/2026.11.2/homeassistant/helpers/service.py#L791-L796)).
3. For each entity, in one loop before any robot is called: read `registry_entry.options["vacuum"]["area_mapping"]`; raise if it is absent; collect segment ids of the requested areas that are keys of the mapping; skip the entity (debug log) when that collects nothing ([services.py#L39-L73](https://github.com/home-assistant/core/blob/2026.11.2/homeassistant/components/vacuum/services.py#L39-L73)).
4. Call `async_clean_segments(segment_ids=[…])` on every entity that has segments ([services.py#L75-L78](https://github.com/home-assistant/core/blob/2026.11.2/homeassistant/components/vacuum/services.py#L75-L78)).
5. **After** step 4, raise `areas_not_mapped` if a requested area was a key of no entity's mapping ([services.py#L80-L86](https://github.com/home-assistant/core/blob/2026.11.2/homeassistant/components/vacuum/services.py#L80-L86)).

One area maps to several segments: calling `clean_area` with one area id cleans **every** segment mapped to that area on that robot ([services.py#L58-L63](https://github.com/home-assistant/core/blob/2026.11.2/homeassistant/components/vacuum/services.py#L58-L63)). There is no core action that cleans one segment by id.

### Calls that succeed and do nothing

No error is raised, the result is a normal success, and no robot is called, when:

- the targeted vacuum is **unavailable**, **disabled** (not loaded, so not a candidate) or does not exist: dropped at [helpers/service.py#L743](https://github.com/home-assistant/core/blob/2026.11.2/homeassistant/helpers/service.py#L743), warning only at [L754-L760](https://github.com/home-assistant/core/blob/2026.11.2/homeassistant/helpers/service.py#L754-L760), return at [L791-L796](https://github.com/home-assistant/core/blob/2026.11.2/homeassistant/helpers/service.py#L791-L796);
- every requested area is a key of the mapping but its segment list is **empty** (`[]`): the area counts as handled, no segment is collected, the entity is skipped ([services.py#L59-L71](https://github.com/home-assistant/core/blob/2026.11.2/homeassistant/components/vacuum/services.py#L59-L71)). The frontend dialog never saves an empty list (next section), but core does not forbid it.

## Gaps for this card

### Epic 3: inputs of the « start a clean » use case (ADR 0003 path 1)

The use case can call `vacuum.clean_area` only when all of these hold, each read and parsed at the adapter boundary:

1. **Robot entity**: a `vacuum.*` entity id known from the registry (`platform`), present in `hass.states` (a missing key means disabled or not loaded).
2. **Availability**: `state` is not `unavailable`. An unavailable or missing target makes the call succeed and do nothing, so the card must check before calling and must not report success from the call alone. Whether `unknown` should block a start is a product choice (`owner-only`).
3. **Feature**: `attributes.supported_features` is a number and `(supported_features & 16384) !== 0`.
4. **Mapping**: `options.vacuum.area_mapping` from `config/entity_registry/get` (or the shared `config/entity_registry/list` read of `ha-core-registries.md`), refreshed on `entity_registry_updated`. Parse it as an object of string to array of strings; ignore keys that are not in `hass.areas` and empty arrays.
5. **Area id**: the area the user tapped, or the area whose segment list contains the tapped room's segment id. The link « card room → segment id » is integration-specific (Roomba+: `docs/research/roomba-plus.md`, #25). Cleaning an area cleans **all** its segments on that robot, so if the card shows one outline per segment, two outlines mapped to the same area start the same job; the confirmation must name the area, not the segment. Core does not stop a segment from being listed under two areas (only the frontend dialog does, see « Rules enforced only by the frontend dialog »; core deduplicates and cleans it once, [services.py#L56-L63](https://github.com/home-assistant/core/blob/2026.11.2/homeassistant/components/vacuum/services.py#L56-L63)): when the tapped room's segment id is found under **more than one** area, the card treats the mapping as ambiguous and uses ADR 0003 path 2, never the first match.
6. **Confirmation**: the confirmation dialog (ADR 0003 point 3) names the robot, the action and the area; nothing is sent until the user confirms, and nothing is sent on hover, load or re-render.
7. **Call**: after confirmation only, one robot and one area per call, `return_response` false: `hass.callService("vacuum", "clean_area", { cleaning_area_id: [areaId] }, { entity_id })`. One area per call avoids the « partly started, then `areas_not_mapped` » case (errors row 7). Whether to pass `notifyOnError = false` (the card shows the error in its own dialog instead of a second toast) is a UI choice.
8. **Result**: success means the integration accepted the command; progress (in progress, done, failed) comes from later `state` changes, never from the call.
9. **Errors**: switch on `error.code` and `error.translation_key` (`area_mapping_not_configured`, `areas_not_mapped`, `service_not_supported`, `service_not_found`, others); show the card's own localised text for known keys and the raw `message` only as a fallback, as text.

### Fallback (ADR 0003 path 2)

The card uses the adapter's own room action when any of these is true: core older than 2026.3.0 (no service: `hass.services.vacuum?.clean_area` absent, errors row 10); the robot lacks `CLEAN_AREA`; `area_mapping` is absent; the room's area is not a key or maps to `[]`; the tapped room's segment id is listed under more than one area (step 5); or the user wants a mode core cannot express. Core has **no** mop notion and `clean_area` has no mode field, so:

- whether a robot vacuums or mops, and the word used in the confirmation (« vacuum », « mop »), must come from the adapter, never from core;
- a mop-only robot that does expose `CLEAN_AREA` cleans in whatever mode the integration picks; a robot that can do both and must mop (for example Roomba+'s `cleaning_mode`, see `docs/research/roomba-plus.md`) needs path 2.

On core 2026.3.x and 2026.4.x, an unmapped area does not raise `areas_not_mapped`; the call succeeds and nothing happens. Checking the mapping before calling (input 4) covers both behaviours, so this is a behaviour to handle, not a requirement; #28 decides the minimum version.

### Security and privacy

1. **Image URLs carry a credential.** The `token` query opens the image to anyone for up to about 10 minutes. The card must never log, persist (config, `localStorage`, error reports) or display image URLs or tokens, and must keep them out of error messages. The same holds for whole state objects and `attributes` of image (and camera) entities: they contain `access_token` (and `entity_picture` with the token), so they are never logged, dumped, put in an error message or copied into a fixture without the capture rule above.
2. **Where the URL comes from.** The project's security rule says « image URLs only from `entity_picture` of known entities » ([`.claude/agents/security-auditor.md`, L11](../../.claude/agents/security-auditor.md#L11)). The source conflicts with it: `entity_picture` can be replaced by the integration with any string ([image/entity.py#L99-L100](https://github.com/home-assistant/core/blob/2026.11.2/homeassistant/components/image/entity.py#L99-L100)), while the frontend builds the URL from `access_token` with a fixed path ([F: src/data/image.ts#L14-L17](https://github.com/home-assistant/frontend/blob/20261028.6/src/data/image.ts#L14-L17)). Options: (a) build `/api/image_proxy/<entity id>?token=<access_token>&state=<state>` exactly like the frontend, for an entity id taken from the registry, each part URL-encoded, fixed path, keeping the `state=` cache-buster; or (b) use `entity_picture` only if it starts with `/api/image_proxy/<that entity id>?token=`. **Open owner decision** (`owner-only`, to record in #29; not answered yet). The security review leans to (a). If (b) is ever chosen, its prefix check must reject `/api/image_proxy/<id>/..`, `/api/image_proxy/<id>x?token=` (another entity id sharing the prefix) and protocol-relative `//host/...`. Either way, never use an absolute URL from an attribute.
3. **Untrusted strings.** Segment `name` and `group`, area ids in `area_mapping`, error `message` and error `translation_placeholders` (set by the integration for integration errors; carrying area or entity ids for core errors) come from integrations or users: render them only through Lit text bindings, including when they are substituted into the card's own localised strings; never use them as HTML, CSS, URL or attribute names.
4. **Untrusted keys.** `area_mapping` keys and segment ids are untrusted: index them in a `Map`, not a plain object.
5. **No polling.** The 5-minute token rotation already produces a state change per image entity; the card reacts to `hass` updates (only re-rendering a plan whose image URL changed) and never fetches images or segments on a timer.

### Upstream

No upstream gap blocks the card, so no issue draft. Observations only: core does not validate the shape of `options.vacuum` (the one-area-per-segment rule lives in the frontend dialog), does not remove deleted areas from the mapping, and returns success for a `clean_area` call on an unavailable vacuum. Questions about Roomba+'s support of `CLEAN_AREA` belong to the Roomba+ research (#26), not to core.

## Relation to ADR 0003 and to the previous document

- ADR 0003 path 1 says « if the robot's room is mapped to a Home Assistant area … call `vacuum.clean_area` with that area ». Confirmed, with two refinements for #29: the mapping is area → several segments, so the call cleans the whole area on that robot; and several failure cases return success silently (unavailable or missing robot, area mapped to `[]`, and before 2026.5.0 any unmapped area), so « errors are shown in the dialog » needs pre-checks, not only error handling. ADR 0003 point 3 (« the action (vacuum or mop) ») cannot come from core.
- ADR 0003 consequences say errors are shown « in plain words, with the integration's message ». Refinement for #29: the card shows its **own** localised text chosen from `error.code` and `error.translation_key`, with the raw `message` only as a fallback (as text), because a core `message` is English-only or a bare translation key (see « Errors ») and an integration `message` is untrusted.
- ADR 0003's « à vérifier » items are settled: field `cleaning_area_id`, feature `CLEAN_AREA = 16384`, first release 2026.3.0.
- Previous version of this document (unverified, 2026-11-20): every claim is confirmed (`clean_area`, mapping in the entity settings, option shown only with the feature, minimum 2026.3), except that the minimum needs the nuance above (2026.3.0 for the feature, 2026.5.0 for `areas_not_mapped`). Its floor and area rows are replaced by the link to `ha-core-registries.md`. No contradiction with `ha-core-registries.md`.
