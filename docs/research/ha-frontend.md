### The general rule for `ha-*` elements

| Fact | Source | What the card does |
|---|---|---|
| « The frontend has no public component library for custom cards. » « Nothing in the frontend repository lists `ha-*` elements as supported, or promises that they stay the same. They are loaded only when the frontend needs them, and they can change in any release. » `ha-card` is « the one exception in practice, not on paper ». « For anything else, like a picker or a form field, build or bundle your own. » « To show a built-in card or one of the standard dialogs inside your card, use the card helpers, which the frontend loads for custom cards on purpose. » | https://contributors.home-assistant.io/frontend/custom-ui/ « Which tools to use » | Every `ha-*` element other than `ha-card` is used only after `customElements.get(tag)` returns a class, with a plain-HTML fallback styled with theme variables. The robot picker (popover and bottom sheet) is the card's own element. The confirmation uses the card helpers (« Dialogs » below) |
| The `hass` property is « the public API for custom cards and panels »; contexts (`context-request` event) are an alternative with no stated stability promise | https://contributors.home-assistant.io/frontend/architecture/hass-and-contexts/ | The card reads only `hass`; it does not use contexts |

**Why the top layer escapes clipping**

| Fact | Source |
|---|---|
| `showModal()` and `showPopover()` add the element to the top layer | WHATWG HTML, « show a modal dialog » https://html.spec.whatwg.org/multipage/interactive-elements.html#show-a-modal-dialog and « show popover » https://html.spec.whatwg.org/multipage/popover.html#show-popover (commit snapshot `e8167f82d318dd935d890bd7bd0196621f83e6e7`) |
| A top-layer element is rendered « as if it were a sibling of the document's root »; « Ancestor elements with overflow, opacity, mask, etc. cannot affect it »; its containing block is the viewport (`position: fixed`). Outcome:

- The picker can live in the top layer, out of reach of `ha-card`'s overflow, section transforms and the editor preview (itself an `ha-dialog` in the top layer: a later `showModal()` stacks above it, confirmed live in § 12). The API that every browser Home Assistant serves has, legacy floor and iOS 16.4 companion app included, is a card-owned **`<dialog>` opened with `showModal()`**: it is what Home Assistant's own anchored popover does. `popover` is modern-build only; if ever used, feature-detect it as the frontend does.
- A modal dialog makes the rest of the page inert and gets Escape (`cancel` event) and focus containment from the browser; the card still sets the initial focus and returns it on close.
- CSS anchor positioning is not available on the modern targets (Firefox 133, Safari 18.2): the card positions the dialog itself, from the room's `getBoundingClientRect()` (viewport coordinates, the same as the top layer's containing block), kept inside the viewport, flipped when there is no room, recomputed on resize and scroll. Bundling `@floating-ui/dom` is the alternative Web Awesome uses (size « à vérifier », under the 20 kB owner threshold if the minified files above are representative).
- Container queries are not on the legacy floor: layout inside the card must work without them (or treat them as an enhancement).

### Differences with the ADRs and the earlier sections

- **« Native HA components » (ADR 0004)**: the contributor docs say the opposite for anything but `ha-card`: `ha-*` elements are not promised, « loaded only when the frontend needs them », and for « a picker or a form field, build or bundle your own ». The native confirmation is reachable on purpose through the card helpers. ADR 0004 should read « native look (theme variables, tokens, HA's standard confirmation through the card helpers) », not « native elements ».
- **Popover / bottom sheet (ADR 0004)**: Home Assistant has the exact component (`ha-adaptive-popover`) but it is **not defined on a dashboard** (confirmed live, § 12); `ha-adaptive-dialog` and `ha-bottom-sheet` are defined only through an accidental import chain. The picker must be the card's own element; it can copy Home Assistant's breakpoint `(max-width: 870px), (max-height: 500px)`. Like `ha-adaptive-popover` (a `wa-popover` opened with `showModal()`), it lives in the top layer (§ 13).
- **Entity settings link (ADR 0003 « Permissions »)**: the ADR says the link is built « on a fixed Home Assistant path ». No route opens one entity's settings; the query parameters `?more-info-entity-id=<id>&more-info-view=settings` do, on any path, but the preferred mechanism is the `hass-more-info` event with `view: "settings"` (§ 14). The ADR wording should follow (follow-up proposed in #99's pull request).
- **`--state-*` (ADR 0004, « à vérifier »)**: now verified. The names are `--state-vacuum-active-color`, `--state-vacuum-error-color`, `--state-active-color`, `--state-inactive-color`, `--state-unavailable-color`; `--state-vacuum-cleaning-color` is not defined (a theme may set it; the frontend's chain reads it first). There is no « done » state colour: use `--success-color`.
- **Motion (ADR 0004)**: Home Assistant already shortens its `--ha-animation-duration-*` tokens to 1 ms under `prefers-reduced-motion`; using those tokens gives the ADR's rule for free (the card still adds its own media query for any keyframes).
- Earlier sections of this document: no contradiction. « `getGridOptions` absent = full width, height follows content » is confirmed in code (`columns: 12`, `rows: "auto"`); a section can span several columns (12 × `--column-span`).

### Gaps for this card

What a UI issue must handle defensively:

1. **`ha-*` may be undefined.** Before using any `ha-*` element except `ha-card`, check `customElements.get(tag)`; otherwise render plain HTML (`<button>`, `<svg>`, `<div role="status">`) styled with theme variables. Never use `ha-adaptive-popover`, `ha-adaptive-dialog`, `ha-bottom-sheet`, `ha-dialog`, `ha-list-item`, `ha-list-item-button` or `ha-form` in the card itself. The live checks (§ 12, sections view, masonry view and card editor preview, 20261028.8) matched the import graph: the guard is still needed because the chains are accidental, not because the elements were missing. At 20261125.0 the chains are the same and `ha-list` / `ha-list-item` no longer exist (§ 15).
2. **Card helpers may be missing** (`window.loadCardHelpers` absent, rejected import, or no `showConfirmationDialog` in the result, for example if the card is rendered outside a dashboard). Fallback: the card's own confirmation element with the same text and buttons, keyboard reachable, Escape cancels.
3. **Confirmation semantics.** `showConfirmationDialog` resolves `true`/`false`; with `action`, a rejected start leaves the dialog open with no message. Pass `text` as a plain string. Show success or failure on the room in every case.
4. **`hass` fields may be `null` or absent** early (`themes`, `user`, `states`, registries) and between versions: optional reads, readable fallback.
5. **Language**: resolve `hass.locale?.language ?? hass.language` against `en`/`fr` (exact, lower-case, base before `-`, then `en`); in `getConfigForm` labels use `document.documentElement.lang`. Never use `hass.localize("ui.…")` keys.
6. **Theme variables** always with a fallback in `var()` (a custom theme may not define them, `--ha-card-border-radius` is not global). State colours through the frontend's chain (§ 6).
7. **Touch targets**: `ha-button` defaults to 40 px; set 44 px minimum (`--ha-button-height` or own buttons).
8. **Focus**: no global `--ha-focus-ring`; use `--ha-color-focus` with a `--primary-color` fallback. A focused SVG `path` with `tabindex="0"` gets the browser's default `:focus-visible` ring in Chromium 158 (§ 12); the card's own `solid` outline on SVG and other engines are « à vérifier », so the card may add a stroke on focus as well.
9. **Picker placement**: a picker rendered in the card's tree can be clipped by ancestors. The card opens its own `<dialog>` with `showModal()` (top layer, supported down to the legacy floor, § 13), positioned by script from the room's `getBoundingClientRect()`; no CSS anchor positioning (missing in Firefox 133 and Safari 18.2), `popover` only with feature detection. The narrow layout (bottom sheet) is the same dialog styled differently.
10. **Preview**: when `preview` is `true`, never start a robot; tolerate being rebuilt on each config change.
11. **Sizing**: return `getGridOptions()` with `rows: "auto"`; handle `layout === "grid"` (fill the cell) and an unknown `layout`; keep `getCardSize()` synchronous.
12. **More info**: `hass-more-info` with `{ entityId }`, `bubbles` and `composed`, dispatched from a connected element.
13. **Re-check at every frontend bump**: the accidental chains (§ 3, § 4, § 8), the dialog-box params, the `MoreInfoView` values and the browserslist floors are internal and can change without notice. Last re-check: 20261028.8 (stable) and 20261125.0 (beta), § 15, with the scripts described there.
14. **Entity settings link** (administrators only): `hass-more-info` with `{ entityId, view: "settings" }`, for an enabled entity and for a disabled one (§ 14). Undocumented for custom cards.
15. **Container queries** are not on the legacy floor (§ 13): layout must not depend on them.

« À vérifier » in this section, and what confirms it:

- Whether a `TemplateResult` from the card's Lit renders inside `dialog-box`: a live test (not needed if `text` stays a string).
- SVG focus outline in Firefox, Safari and the companion apps, and the card's own `solid` outline with offset on SVG in any engine (Chromium default ring done, § 12): `/ha-live-test`.
- The card's `showModal()` picker in a sections view, in a masonry view and on iOS: `/ha-live-test` (the editor preview is done, § 12).
- `hass-more-info` with `view: "settings"`: what a non-admin sees is done (§ 14). Still open: the message a non-admin gets when a save is refused, and an administrator on a disabled entity.
- Minimum Android System WebView a companion app user can have: Google's WebView support policy or the Android app's issues.
- The real build date of 20261028.6 (changes the modern Edge floor only, 131 or 132): the frontend's release workflow run for the tag.
- Bundled size of `@floating-ui/dom` 1.8.0 with its core, if ever needed: the card's build report.
- Whether `anchor-name` / `position-anchor` resolve across the card's shadow root and a top-layer element: CSS Anchor Positioning 1, tree-scoped names (moot while the card positions by script).

No upstream issue is proposed: the frontend states on purpose that `ha-*` elements are not a public API, and the card helpers already give custom cards the standard confirmation.
